# Base Controller

## Overview

Base is an STM32F103C8T6 controller project intended to provide a reusable foundation for the Cartesian robot controller. It is newer and more structured than Alpha, and it uses CMake presets together with the STM32 HAL/CMSIS sources generated by CubeMX.

Base is currently a platform/prototype project. Its GPIO configuration, generated headers, application code, and physical wiring must be checked together before it is used on a robot.

## Project structure

```text
Controller/Base/
├── README.md
├── Base.ioc
├── CMakeLists.txt
├── CMakePresets.json
├── STM32F103xx_FLASH.ld
├── Core/
├── Drivers/
├── cmake/
│   ├── gcc-arm-none-eabi.cmake
│   ├── starm-clang.cmake
│   └── stm32cubemx/
├── startup_stm32f103xb.s
└── .vscode/
```

`Base.ioc` is the CubeMX configuration source. `CMakeLists.txt` defines the build target, while `CMakePresets.json` provides Debug and Release configurations.

## Target hardware

| Item | Configuration |
|---|---|
| MCU | STM32F103C8T6 |
| CPU | ARM Cortex-M3 |
| System clock | 72 MHz |
| External oscillator | 8 MHz HSE |
| Flash | 64 KB |
| RAM | 20 KB |
| Debug | SWD |
| Framework | STM32 HAL and CMSIS |

The clock configuration uses the 8 MHz HSE with PLL multiplier 9 to obtain a 72 MHz system clock.

## Pin mapping

The intended Base configuration in `Base.ioc` is:

| Function | Pin |
|---|---|
| X direction | PB0 |
| X step | PB1 |
| Y1 direction | PB4 |
| Y1 step | PB5 |
| Y2 direction | PB6 |
| Y2 output currently labeled `DIR_Y2` in `Base.ioc` | PB7 |
| USART1 TX/RX | PA9/PA10 |
| USART2 TX/RX | PA2/PA3 |
| USB DM/DP | PA11/PA12 |

USART1 and USART2 provide two serial communication channels. The USB pins are configured for USB device support in the CubeMX project.

## Application role

Base is intended to provide the basic controller platform for:

- X-axis step/direction control;
- two synchronized Y-axis motor channels;
- UART communication;
- future controller-to-controller communication;
- future expansion with sensors and machine peripherals.

The exact application behavior is defined by the current source under `Core/Src`. The `.ioc` configuration alone does not determine the complete machine protocol. In particular, `Base.ioc` currently labels both PB6 and PB7 as `DIR_Y2`; the second Y motor step signal is not clearly represented by the generated labels. This must be resolved before connecting the second Y driver.

## Build system

Base uses CMake with Ninja and ARM GCC. The important files are:

```text
CMakeLists.txt
CMakePresets.json
cmake/gcc-arm-none-eabi.cmake
cmake/stm32cubemx/CMakeLists.txt
```

Required tools include:

```text
cmake
ninja
arm-none-eabi-gcc
arm-none-eabi-g++
arm-none-eabi-objcopy
arm-none-eabi-size
```

Build Debug firmware with:

```bash
cd Controller/Base
cmake --preset Debug
cmake --build --preset Debug
```

Build Release firmware with:

```bash
cd Controller/Base
cmake --preset Release
cmake --build --preset Release
```

Build output is normally placed under:

```text
Controller/Base/build/Debug/
Controller/Base/build/Release/
```

The linker script is `STM32F103xx_FLASH.ld`, which defines the STM32 Flash and RAM layout.

## Flashing and debugging

Base requires an SWD programmer/debugger, normally ST-LINK. Flashing can be performed through STM32CubeIDE, STM32CubeProgrammer, OpenOCD, or another compatible STM32 programmer.

Example STM32CubeProgrammer command:

```bash
STM32_Programmer_CLI -c port=SWD \
    -w build/Debug/Base.elf \
    -rst
```

The exact output filename depends on the CMake configuration.

## Expected behavior after flashing

After reset, Base should:

1. initialize the STM32 HAL;
2. configure the system clock;
3. initialize configured GPIO pins;
4. initialize the configured UART and USB peripherals;
5. enter the application main loop;
6. wait for the command or control behavior implemented in `Core/Src/main.c`.

The expected physical result depends on the current Base application code and the connected hardware. Flashing Base does not automatically guarantee Cartesian movement, because the motor driver wiring and application command path must match the project configuration.

## Important verification checklist

Before connecting motors, verify:

1. `Base.ioc` pin names match `Core/Inc/main.h`.
2. `Core/Src/main.c` writes the intended step pins.
3. Direction polarity matches the mechanical direction.
4. Driver enable polarity is correct if enable signals are added.
5. The board uses the expected 8 MHz oscillator.
6. STM32 ground and motor-driver logic ground are connected.
7. Motor power is supplied separately and safely.
8. The first test is performed at low speed with a physical stop or emergency-stop available.

The Base and Alpha projects use different pin maps. Firmware built for one project must not be flashed onto hardware wired for the other without reviewing the wiring.

## Limitations

- Base is a foundation/prototype rather than a complete machine controller.
- No general homing and calibration sequence is defined.
- No encoder feedback is present in the basic configuration.
- Motion functions may be blocking.
- UART command buffering and acknowledgment behavior require further development.
- Acceleration and deceleration are not generally implemented.
- Sensor timeout and emergency-stop handling are incomplete.

## Relationship to other projects

```text
Alpha  →  Base  →  Master
```

Alpha is the FreeRTOS/USB-enabled controller project. Base provides a simpler STM32/CMake foundation. Master provides a separate integrated conveyor, sensor, downstream-UART, and pick/drop workflow.
